# Configuration and secrets

Runtime settings use schema version 4 and are stored beneath the current user's local application-data directory. `src/GameLingoAI.App/appsettings.sample.json` is a sanitized example, not a runtime secret file.

Current source supports the process environment variable `GAMELINGOAI_DATA_ROOT` to select a dedicated absolute local directory before startup. Settings, SQLite, OCR models, region drafts and production logs all use this root. An unset variable preserves the existing LocalAppData default; invalid, relative, network/device, drive-root or unavailable-drive selections fail without falling back. Resolution alone creates no files. No existing data is moved, copied or deleted. A new directory starts with no configured providers/models; the user must configure it explicitly. This does not relocate Ollama models, Windows Credential Manager, OS-managed data or TEMP/TMP; a launcher must separately route its own temporary files. Package0.1.0.15 predates this change and does not support the override yet.

## Safe defaults

- Capture runs at 8 FPS with a capacity-two queue.
- Overlay defaults use local Segoe UI 30 DIP semibold, white text/black 1.5 DIP outline, three lines, 1,000 characters, 0.9 client-width ratio, centered bottom anchor, -24 DIP vertical offset, and 0.55 black background opacity. Font names cannot contain file/URI syntax; colors use `#RRGGBB`. These optional schema-v3 additions preserve old files' defaults. See `OVERLAY_DESIGN.md` for explicit interactive editing and verification.
- OCR confidence starts at 0.65 and stabilization requires two observations within 600 ms. Schema v3 adds average-confidence (0.65), text-similarity (0.88), spatial-overlap (0.2), immediate-change confidence (0.97), two-frame disappearance, eight-candidate, and 128-span bounds. v1/v2 files migrate with these conservative defaults.
- Remote-text consent, history, diagnostic screenshots, and recognized-text logging are disabled.
- Cache is independent of history: defaults are 100,000 rows, 500 MiB of accounted payload, 30 days, 64-row pruning batches, 32 active distinct request keys, and 64 waiters per key. `maximumRows: 0` disables storage. The added age/pruning/admission fields are optional schema-v3 additions with safe defaults for existing files. See `TRANSLATION_CACHE.md`.
- Providers require HTTPS. Plain HTTP is accepted only for an Ollama provider whose host resolves as an explicit loopback URI.
- OpenAI-compatible providers must explicitly set `endpointDialect` to `chatCompletions`, a secret reference, a selected model, temperature between 0 and 2, and `maximumOutputTokens` between 1 and 4096. The base URL must be an HTTPS prefix ending in `/`, with no embedded credentials, query, or fragment.
- Ollama providers may omit `baseUri` to use `http://127.0.0.1:11434/`; explicit non-loopback endpoints require HTTPS. A local model name is required, but no secret reference is needed by default. The adapter never downloads a missing model.
- Custom HTTP providers use a nested `customHttp` mapping with its own `version: 1`, an allowlisted POST/PUT method, fixed credential-header secret references, a bounded JSON value-token body, and a restricted response path. Remote destinations require public HTTPS; explicit `localOnly` permits loopback only. See `docs/CUSTOM_HTTP_PROVIDER.md` for the exact grammar and SSRF restrictions.

Validation aggregates field paths and actionable messages before a session starts. It covers schema version, capture/OCR/stabilization ranges, BCP 47 language tags, provider identity/model/timeout/URL, cache limits, overlay limits, and logging privacy.

## Hotkey configuration (TASK-020 accepted)

Schema v4 adds `hotkeys: { "enabled": false, "bindings": [] }`. Each binding contains `action` (`start`, `pauseResume`, `stop`, `toggleOverlay`, `emergencyStop`), flags `modifiers` (Control and/or Alt, optionally Shift), and `key` (A-Z, 0-9, F1-F11; case-insensitive). There are at most five bindings, with unique actions and key combinations. Bare or Shift-only keys, Windows-key combinations, Alt+F4 and F12 are rejected. F12 is reserved by Windows for debugging; the adapter uses supported [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey) registration, not input hooks.

Legacy v1/v2/v3 files migrate in memory to v4 with hotkeys disabled and empty, even if an unknown legacy `hotkeys` field exists. The Profiles/Settings page exposes shortcut definitions: select actions, modifiers and key names, then explicitly Load, Save, Apply for this run, or Disable now. Load and Save never register keys. Each launch starts inactive even when definitions were saved as enabled; Apply is required. Disable releases registrations without changing saved definitions. Dirty drafts require confirmation on Load or application exit; file operations prevent concurrent draft edits and cancel/drain on shutdown. Hotkeys are local application settings, not portable game-profile settings; configuration export retains definitions but never any keyboard-event history. Applied actions route to guarded session commands, including explicit subtitle suppression and emergency stop; see `SESSION_PIPELINE.md` for lifecycle behavior and verification limits. TASK-020 was accepted on 2026-09-29 after automated, physical-key and user-observed checks.

`WindowsHotkeyService` owns registrations for a current-thread, current-process HWND. The host must forward only its own window messages and dispose the service before destroying that HWND. Registration uses `MOD_NOREPEAT`; dispatch requires matching live ID, modifiers and key. IDs are not reused during the process lifetime, so queued messages from replaced configurations cannot execute a newly assigned action. Identifier exhaustion fails explicitly and requests an application restart. Invalid definitions preserve existing registrations; a valid replacement first releases previous definitions, and any subsequent registration failure rolls back the new set. This replacement policy deliberately reports failure rather than claiming the old set remains active.

Clear suppresses dispatch before unregistering. Failed releases remain tracked and retryable; no new registration is admitted until they release. Dispose reports release failure and can be retried on the owner thread. Native errors use fixed actionable messages, without logging raw key events. Tests exercise fake rollback/release failure and real Windows conflict, own message-only HWND notification dispatch and release/re-registration. The native notification test alone is NOT proof of physical key delivery. A separate real-key run on 2026-09-29 received all five actions and 16 foreground-other notifications without synchronous focus change; release/re-registration passed. Session integration tests prove emergency hide/cancellation notification within two seconds, separately from eventual native cleanup. The user confirmed normal visual behavior and no delayed focus stealing; see `SESSION_PIPELINE.md` and `TASK_EXECUTION_PROGRESS.md`.

`GlobalHotkeyHost` lazily creates an application-owned message-only HWND on first enabled Apply. It forwards only WM_HOTKEY to the registration adapter and contains managed callback failures at the native boundary. Shutdown releases registrations before destroying this HWND. No visible focus-taking window or keyboard listener is created. `--synthetic-test` now isolates both its database and configuration JSON in its temporary directory, so manual hotkey-save acceptance does not change formal user settings.

## Secrets

API keys are stored as generic credentials in Windows Credential Manager for the current user. JSON settings contain only an opaque `secretReference`; they never contain the key, authorization header, or credential blob. Sanitized export removes secret references, forces recognized-text logging off, and disables diagnostic screenshots.

Never place an API key in `appsettings.sample.json`, tracked JSON, command-line arguments, or logs.

## Migration and recovery

Schema v1 first adds the disabled diagnostic-screenshot privacy setting. Schema v1/v2 then gain bounded stabilization defaults while preserving existing observation count/window values. All v1/v2/v3 files migrate in memory to v4 with inactive hotkeys. Saving writes a temporary file and atomically replaces the settings file. Corrupt JSON, invalid settings, missing schema versions, and newer unsupported schema versions return a typed, correlated failure without overwriting the source file.
